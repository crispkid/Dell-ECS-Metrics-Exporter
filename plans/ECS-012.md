# ECS-012 v1.0.0-rc.1 Release

## Purpose and Observable Outcome

Finish the repository-owned V1 development work and publish `v1.0.0-rc.1` as an explicitly
marked GitHub Pre-release. The RC must provide installable, traceable and signed artifacts without
claiming the stable production certification that still depends on external ECS and deployment
environments.

## Decision

- Target version: `v1.0.0-rc.1`.
- A tag containing a Semantic Version prerelease suffix uses the RC path.
- RC publication still requires deterministic verification, race detection, container startup,
  Kubernetes schema validation, synthetic target scale, source/license and two-platform image
  vulnerability scans, SBOMs, signatures and OCI provenance. GitHub-native attestations remain
  mandatory for public/Enterprise repositories and for stable publication.
- Only prerelease tags may skip the exact production ECS 3.8.1.4, exact CE 3.8.0.3, deployed E2E
  and deployed performance jobs.
- A stable tag cannot publish unless all protected external jobs succeed.
- Release notes and README must state that the RC is for evaluation and integration testing, not
  stable production approval.

## Known External Limitations

The stable-only exact appliance, tagged deployed E2E, deployed target-scale and named approval
evidence remain outside this RC. Local Docker, kubeconform and external SBOM scanner availability
does not substitute for the GitHub tag workflow; if that workflow fails, publication is blocked
until the failing gate is corrected.

The configured GitHub repository is private. GitHub documents native artifact attestations for
private repositories as an Enterprise Cloud feature. The private RC therefore records a signed
boundary asset and retains Cosign, SBOM and BuildKit OCI provenance; stable still runs the native
attestation actions and fails if the repository plan is insufficient.
