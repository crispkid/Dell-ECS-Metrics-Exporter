# ECS-008 Execution Plan

## Purpose and Observable Outcome

Prepare the exporter for a controlled production release without treating the
known ECS CE Flux limitation as a product defect. The observable result is a
release candidate that supports local binary, Docker/OCI, Kubernetes/Helm, and
Linux bare-metal/systemd deployment; has deterministic security, supply-chain,
deployment, performance, and live-certification entry points; and refuses to
claim production readiness when required external evidence is absent.

## Context and Constraints

- Governing contracts: `SPECIFICATION.md` REQ-001 through REQ-012, especially
  deployment/non-functional sections 19–21 and compatibility sections 22–25.
- Target production build: physical ECS `3.8.1.4`; test evidence currently
  available only for partial Management API behavior on ECS CE `3.8.0.3`.
- ECS CE does not contain the full production Flux monitoring stack. The
  exporter must preserve degraded Management API operation instead of treating
  CE Flux HTTP 503 as a release failure.
- A live ECS certification requires a protected, non-production account or
  explicitly authorized read-only production endpoint. Mock/component evidence
  cannot populate Profile `tested_builds`.
- Release tooling must not embed credentials, private endpoints, raw ECS
  responses, or long-lived signing keys.
- Repository commits, remotes, tags, releases, registry pushes, and production
  deployments remain externally visible actions and are not performed unless
  explicitly requested and configured.

## Decision Log

- 2026-07-26 — Bare Metal means a Linux systemd deployment using a dedicated
  unprivileged account, read-only configuration/profile paths, external secret
  files, systemd sandboxing, and an explicit localhost/default listen policy.
- 2026-07-26 — Release signing uses keyless Sigstore/OIDC in protected CI;
  no private signing key is stored in the repository.
- 2026-07-26 — Release artifacts include Linux amd64/arm64 binaries, profiles,
  systemd assets, Helm chart, checksums, SBOM, provenance/attestation, and a
  multi-architecture OCI image referenced by digest.
- 2026-07-26 — Real ECS certification, container startup, live Kubernetes, and
  external vulnerability evidence become fail-closed release gates. Their
  scripts may report blocked when prerequisites are absent, but a blocked gate
  cannot authorize a production release.
- 2026-07-26 — Existing ECS 3.6/3.7/3.8.0/3.8.1 Profiles remain
  documentation/component support until an exact build passes the certification
  gate; production support claims must name only certified builds.

## Implementation Plan

1. Add `deploy/bare-metal/` systemd/sysusers/tmpfiles assets and safe
   install/upgrade/uninstall/verify scripts.
2. Extend Helm NetworkPolicy for explicit ingress selectors and bounded egress;
   add Kubernetes schema/policy checks when the configured tools are available.
3. Add supply-chain/release scripts that build reproducible artifacts, validate
   versions, create checksums/SBOM/provenance inputs, and fail on missing tools.
4. Add protected GitHub workflows for release and self-hosted ECS certification,
   with least-privilege permissions and full-SHA-pinned actions.
5. Add live-certification, deployed E2E, container smoke, and performance gates.
   Preserve a strict evidence boundary between mock, partial-live, and certified
   results.
6. Add a production runbook, release checklist, and alerting rules; update the
   README and all governed contracts.

## Recovery and Idempotence

Bare-metal installation stages files atomically and preserves operator-owned
configuration and secrets during upgrades. Uninstall requires an explicit flag
before deleting configuration. Release scripts write only to ignored build and
evidence directories and may be safely rerun. Helm and OCI release artifacts are
immutable; rollback uses a previously verified digest and Helm revision.

## Outcomes and Retrospective

Implementation is complete for the repository-controlled scope:

- deterministic Linux/macOS archives, Helm package, checksums and release
  metadata were produced twice with identical SHA256 manifests;
- unit/component and fresh race suites passed; coverage is 84.3%; Profile
  validation, synthetic 10/100/10,000 performance, Helm/Bare Metal static
  checks, CI policy, governance doctor, and checksum verification passed;
- Bare Metal upgrade now restarts the service and restores the previous binary,
  Profiles, and systemd unit when the upgraded service fails to start;
- all absent production prerequisites return a blocking status rather than a
  skipped or successful result.

Gate 4 remains unapproved. The current repository implementation is untracked
and has no remote; the Docker daemon, kubeconform, Syft, Grype, OSV-Scanner,
promtool, and a Linux systemd host are unavailable; the external Go
vulnerability database could not be resolved; and exact ECS `3.8.1.4`,
deployed target-scale, live Kubernetes, signed registry/release, and named
reviewer evidence have not run. The ECS 3.8.1 REST reference is still
login-gated and unreviewed, so the formal Profile evidence remains intentionally
unset. No production approval or exact-build Profile certification is recorded
until those gates pass.
